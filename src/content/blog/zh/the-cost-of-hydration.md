服务端渲染（SSR）解决了白屏问题：HTML 到达，浏览器完成绘制，用户看到了内容。随后，前端框架在客户端下载、解析并执行，遍历刚刚接收到的 DOM 树，重新建立服务端早已知晓的一切。

第二步就是水合（Hydration），而它绝非免费。对于一个主要由文本组成的页面来说，水合是挡在“可见”与“可用”之间最大的单体障碍。

## 可见并不等于可交互

这种时间差很容易被忽视，因为页面 *看起来* 已经完成了渲染。内容已经绘制，没有加载动画。但使菜单打开的 JavaScript 尚未运行，因此点击没有任何反应，用户不得不再次点击。

这正是 Interaction to Next Paint (INP) 指标真正捕捉到的痛点，也是为什么页面在 Paint 指标上得分很高却依然让人感觉卡顿的原因。框架必须先下载、解析、执行，然后才能绑定事件监听器——在此期间，主线程正忙于计算，每一次输入都在队列中等待。

对于典型的营销页或内容页来说，水合工作几乎完全是浪费的，因为框架正在重建的组件永远不会发生改变。静态文本根本不需要组件实例。

## Islands 架构：只水合动态组件

Islands 架构反转了这种默认行为。页面本身是纯 HTML，单个组件显式 *选择* 传输 JavaScript，每个组件成为一个独立的根节点并包含自己的 bundle。

```astro
---
import ThemeToggle from '../components/ThemeToggle';
import WaveField from '../components/WaveField';
---

<h1>静态标题 — 零 JavaScript</h1>

<ThemeToggle client:load />
<WaveField client:visible />
```

`client:` 指令是非常精妙的设计，因为它使加载策略变成了组件自身的属性，而非框架级别的全局配置：

- `client:load` — 立即水合。适用于首屏上方必须立即响应的任何交互。
- `client:idle` — 等待 `requestIdleCallback`。适用于可以延迟片刻的控制组件。
- `client:visible` — 等待 IntersectionObserver。适用于首屏下方所有内容的理想默认值，对昂贵组件至关重要。
- `client:only` — 完全跳过服务端渲染。当组件依赖没有服务端替代品的浏览器 API 时不可或缺。

`client:visible` 是让重型组件变得可接受的关键。本站首页上的 3D 波浪场引入了一个 WebGL 库，其体积远大于页面上其他所有代码的总和。因为它是 Island，该代价被拆分为独立的代码块，仅在元素滚动到视口时才会被获取——如果你从不向下滚动，或者 WebGL 不可用，你就永远不必付此代价。页面上的其他任何内容都不会等待它。

## 你在做的权衡

Islands 并不是单方面的完美方案。它是一种权衡，且这种权衡非常真实：

**状态无法跨越 Island 边界。** 两个 Island 是两个独立的 React 根节点。它们无法通过组件树共享 context 或 store。你必须通过 URL 状态、`localStorage`、自定义事件或跨框架的订阅 store 库来进行协调——这些都比直接传 prop 带来更多摩擦。

**服务端渲染的标记可能与客户端矛盾。** 读取 `localStorage` 的主题切换按钮在服务端和客户端会渲染出不同的内容。你需要通过在绘制前执行阻塞的内联脚本来决定主题，并让 Island 读取该脚本的决定，而不是再次自行判断。

**Island 会急剧增多。** 如果每三个元素中就有一个需要交互，你就得到了一个步骤更多、体验更差的普通框架页面。该模型在交互占比很小的情况下（博客、文档、营销网站）收益最高。而对于几乎所有内容都有状态的应用外壳（App Shell），单个根节点才是更简单、也可能更快的方式。

## 值得思考的问题

不要问“哪个框架最快”，而是问：*这个页面中究竟有多大比例真正需要交互？*

如果答案是大部分，那就发布一个 App。如果答案是一个主题切换器和一个搜索框——对于像本站这样的博客而言确实如此——那么传统方案发送的大部分 JavaScript，都只是在重新构建从第一个字节开始就已经正确躺在 HTML 里的段落而已。
