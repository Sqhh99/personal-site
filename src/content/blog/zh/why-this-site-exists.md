工程问题中最有趣的部分很少是最终答案，而是促成该答案的前提约束——而这恰恰是在 commit message 中被删除、在文档中被遗漏，并且在六个月后有人询问“为什么会这样工作”时已经彻底丢失的东西。

本站就是我记录这些内容的地方。

## 这里包含什么

四个主要方向，大部分是因为它们在实践中往往最终指向同一种问题：

- **WebRTC 与实时媒体** — 信令、ICE、媒体传输管线、延迟预算。
- **PyTorch 与深度学习** — 训练循环、性能剖析、推理性能。
- **Web 工程** — TypeScript、渲染策略、传输更少的 JavaScript。
- **系统与性能** — 并发、背压、内存与测量。

视频掉帧与训练步骤停滞，本质上是从不同角度观察到的同一个问题：上游生产的速度快于下游消费的速度，且事先没有明确规定接下来该发生什么。

这里的文章试图将条件与结论紧密贴合在一起。测量了什么、在何种硬件上、在何种负载下，以及什么情况会导致结论失效。没有附加条件的基准测试只不过是一段轶事。

## 本站是如何构建的

上一个版本是一个单独的 HTML 文件，加上大约七百行手写的 JavaScript，通过字符串渲染整个 DOM，其中还包括我自己写的一个小型 Markdown 解析器。它能工作，但也走向了死胡同：没有类型，没有路由，文章隐藏在查询参数后面，搜索引擎爬虫根本无法发现它们。

现在的版本是基于 [Astro](https://astro.build) 和 Content Collections 构建的。文章是 Markdown 文件，带有经过 Zod 验证的 frontmatter schema，这意味着标签名称中的拼写错误会在构建时直接报错，而不是渲染出一个空过滤器。每篇文章都是一个真实的、静态生成的 URL。

只有三个组件会传输 JavaScript：主题切换器、文章列表页的搜索与标签过滤器，以及首页的着色器波浪场。其他所有内容在离开服务器时都是纯 HTML。过滤器的设计非常考究，文章卡片均由服务端渲染，React Island 仅仅切换它们的可见性——无论 JavaScript 是否运行，完整的文章列表都已经在 HTML 中了。

样式使用 Tailwind v4，色彩板定义为 CSS 自定义属性，并通过 `@theme inline` 暴露出来，因此亮色和暗色主题是在运行时动态切换，而不是在构建时硬编码。字体选用了 Newsreader 和 Inter。

它作为静态文件部署到 Cloudflare Workers Static Assets。没有服务器，没有数据库，也没有比 `astro build` 更复杂的构建步骤。

## 立身准则

在问题依然令人困扰的时候就把文章写下来。一旦某个问题被彻底理解，它就会变得显而易见；而显而易见的事情往往不会被记录下来——这也正是为什么同一种问题第二次遇到时，依然会浪费一整个下午。
